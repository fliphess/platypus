# Platypus repository review — 2026-10-25

## Scope and assessment

This is a review of the entire available working tree, including staged,
unstaged, and untracked work, rather than a branch diff. There was no resolvable
HEAD commit when the review started. Other agents were changing files during
the review; line references identify the observed snapshot and may move. In
particular, timezone and secret-restoration work appears to be in progress.
No application code, configuration, tests, or existing documentation was changed
by this review. This report is the only file created by the reviewer.

The foundations are good: small Go packages, explicit dependency wiring,
central authorization, a dedicated sensitive-value type, escaped templates,
restrictive browser policy, shared store contract tests, and documented trust
boundaries. Most individual functions are straightforward to read. A wholesale
rewrite or more elaborate framework would make this worse.

The main weakness is consistency across boundaries. AWS writes, database audit
events, catalog refreshes, and browser fragments have different failure and
lifecycle semantics depending on the operation. A human can understand each
piece but has to reconstruct the overall contract. Several defects below come
directly from that gap. Current passing checks do not establish release readiness.

Findings are source-confirmed unless explicitly described as conditional,
environment-specific, or a design observation. Security severity is qualitative,
not a calculated CVSS score. No production testing or exploit attempts occurred.

## Security and audit

### R01 — High: value forms default to GET when JavaScript is unavailable

**Evidence:** `internal/web/templates/item_form.html:11`, value textarea at
`:83`; `internal/web/templates/security.html:82` has the same form defect for
TOTP confirmation.

The item form supplies `hx-post` but no native `method` or `action`. If htmx is
blocked, unavailable, or fails to initialize, submitting Create/Save performs
the browser's default GET submission to the current page. The named value field
then enters the URL, browser history, and potentially gateway/access logs. This
violates the explicit rule that values never enter URLs. CSP and `no-store` do
not prevent form serialization into a URL.

**Recommendation:** Give sensitive forms a safe native POST action and CSRF
field, even if the normal experience requires JavaScript. Add a browser test
with scripts disabled or htmx unavailable that verifies no value enters any URL.

### R02 — Medium: admin elevation persists when its audit record fails

**Evidence:** `internal/web/handlers_adminmode.go:66-72`.

`SetAdminMode` commits before `Audit.Record`. Audit failure returns an error to
the browser, but the next request still has elevated privileges. This requires
an eligible administrator and successful second-factor verification; it is an
audit-integrity defect, not a demonstrated MFA bypass.

**Recommendation:** Commit session elevation and its database audit event in
one transaction, with consistent handling of the external log copy.

### R03 — Medium: pruning can delete audit records without an audit event

**Evidence:** `internal/audit/trail.go:132-146`.

Each deletion batch commits before the pruning event is written. A later batch
failure, cancellation, or final audit failure can leave deleted records with no
record of the pruning action. This contradicts the stated pruning guarantee.

**Recommendation:** Durably record an authorized pruning attempt before the
first deletion, and record progress/completion so partial work remains traceable.

### R04 — Medium, conditional: cleaning group identifiers aliases identities

**Evidence:** `internal/auth/groups.go:59-67`,
`internal/access/teams.go:36`, `internal/textclean/textclean.go`.

Group names are passed through free-text cleaning before matching policy-bearing
teams. HTML removal, entity decoding, control removal, and whitespace trimming
are lossy. Distinct identifiers such as `payments` and `payments<b></b>` can
become the same group. Security impact depends on the identity provider allowing
colliding names and an attacker being able to join or create the other group.

**Recommendation:** Match stable opaque group IDs exactly. If identifiers need
validation, reject invalid input rather than changing its identity. Update the
repository's free-text rule to distinguish display text from authorization IDs.

### R05 — Medium: group synchronization grants and revokes in separate commits

**Evidence:** `internal/access/users.go:64-86`.

Storing reported groups, adding memberships, and removing old memberships are
separate database operations. A removal failure leaves prior additions committed
and skips the membership event. Concurrent requests can observe mixed old/new
memberships. A subsequent successful request may repair state, but that does not
make the intermediate permissions or missing event correct.

**Recommendation:** Synchronize memberships and record the database audit event
in one transaction, with serialization appropriate to concurrent logins.

### R06 — Medium, provider dependent: absent email verification is accepted

**Evidence:** `internal/auth/signed.go:73-79`; `identityFromClaims` is shared
with OIDC login.

An explicitly false `email_verified` is rejected, but an absent claim is accepted.
Because email selects the existing account, a provider exposing mutable,
unverified email without that claim can enable impersonation. This is not proof
that the configured providers are exploitable. Some trusted proxies legitimately
omit the claim, so compatibility needs an explicit policy rather than an implicit
assumption. The threat model currently promises that unverified email is refused.

**Recommendation:** Require explicit verification for providers that supply it,
or explicitly configure and document the trusted identity-claim contract.

### R07 — Low: passkey ceremony state is cleared without atomic consumption

**Evidence:** `internal/web/handlers_adminmode.go:107-111`,
`internal/web/handlers_security.go` passkey completion,
`database/queries/sessions.sql:22-23`.

Requests read ceremony state into memory and then clear it independently. Two
concurrent requests can retain the same challenge and both attempt validation.
Credential counters do not universally solve this because some authenticators
are counterless. This weakens single-use semantics; it does not itself establish
an authentication bypass.

**Recommendation:** Atomically consume and return unexpired ceremony state with
an update/delete returning the state; only one request should obtain it.

### R08 — Medium: rollback previews bypass the reveal timeout

**Evidence:** `internal/web/templates/partials.html:70-81`,
`internal/web/static/app.js:13-18,86-89`.

The rollback preview displays an authorized historical value in a plain `pre`
without the normal hide timer or Hide now control. It can remain visible
indefinitely. Escape closes the native dialog without calling `closeDialog`,
so the secret also remains in the closed dialog's DOM until replacement. This
conflicts with the unattended-screen defense documented for revealed values.

**Recommendation:** Use the same timed reveal component for rollback values,
and clear sensitive dialog contents on the native `close` event as well as the
Cancel button. Decide and document the separate lifetime of values actively
being edited.

### R09 — Medium: the deployable minimal example contains an accepted public key

**Evidence:** `charts/platypus/ci/minimal-values.yaml:7-12`,
`internal/config/config.go:30` and `validate`'s encryption-key checks.

The minimal values file creates a Secret containing a fixed public encryption
key. The chart defaults to `prd`. Configuration rejects the specific public
Compose key outside test mode but accepts this different example key. Someone
replacing the example database password and copying the rest can deploy a known
encryption key, weakening protection of encrypted second-factor state. This is
an unsafe example, not evidence of a private credential disclosure.

**Recommendation:** Make installation examples require a generated key or an
existing Secret; keep rendering-only fixtures clearly separate. Reject known
public example keys outside test mode as an additional guard.

## Correctness and consistency of item operations

### R10 — Medium: cached SSM tags make Terraform protection stale indefinitely

**Evidence:** `internal/items/items.go:103-115,126-135`,
`database/queries/items.sql:9-28`.

SSM tags are fetched once. Parameter sync upserts never refresh or invalidate
them, even when the parameter changes. Adding the Terraform tag later therefore
does not prevent edits; removing it can leave edits blocked indefinitely. Also,
tag-read access denial is treated as no known tags, which allows mutation despite
an unknown management state. This is a product guardrail failure, not a bypass
of the central user permission check.

**Recommendation:** Define freshness and unknown-tag behavior explicitly;
refresh tags and check authoritative management state before mutation.

### R11 — Medium: stale secret-description forms overwrite later edits

**Evidence:** `internal/catalog/catalog.go:129-135`,
`internal/store/awsstore/secrets.go:152-165`,
`internal/store/storetest/storetest.go:258-268`.

The concurrency token is only the current value version ID. Description changes
do not change that ID, so two forms opened at the same time can overwrite each
other's descriptions arbitrarily later. This is broader than the accepted AWS
race between a fresh check and a write in one round trip.

**Recommendation:** Include metadata in the expected revision/fingerprint and
compare against a fresh description before writing. Retain documentation of the
residual AWS race.

### R12 — Medium: a delayed sync can overwrite a newer web catalog refresh

**Evidence:** `internal/itemsync/itemsync.go:92-101`,
`database/queries/items.sql:9-28,36-56`.

A sync callback can carry metadata observed before a web update. Both catalog
upserts overwrite rows unconditionally, including `synced_at`, so a callback
landing after the web refresh restores an older version, description, or
deletion state. Access may reset and temporarily hide the item as well.

**Recommendation:** Prevent old sync observations from overwriting rows refreshed
after the sync began. Separate “seen in this run” bookkeeping from metadata
freshness so deletion detection remains correct.

### R13 — Medium: clearing an SSM description appears to succeed but preserves it

**Evidence:** `internal/store/awsstore/parameters.go:163-165`,
`internal/store/memstore/memstore.go:166-169`,
`internal/items/change.go:193-228`.

The form and preview accept an empty replacement description and audit it as a
change, but the AWS adapter omits the empty description and the memory adapter
explicitly retains the old description. The old text returns after saving,
potentially with an unnecessary new parameter version and misleading audit data.

**Recommendation:** Define clear-description semantics across the service and
both adapters. Implement removal if supported, otherwise refuse it clearly.
Add a shared contract scenario for nonempty-to-empty descriptions.

### R14 — Medium: multi-step AWS writes can partially succeed without success auditing

**Evidence:** `internal/items/change.go:225-228,252-267`,
`internal/store/awsstore/secrets.go:126-149`.

A secret value is written before its description. If the second step fails, the
request reports failure although the live value changed, and the successful
value change never reaches the allowed-update audit call. Retrying can conflict.
Similarly, adapters that write and then `Describe` conflate refresh failure with
write failure. Database transactions cannot make AWS and Postgres atomic.

**Recommendation:** Define explicit partial-success outcomes, audit successful
irreversible steps, and reconcile cache state separately. Use failure-injection
tests after each external step; avoid simply wrapping this flow in a DB transaction.

### R15 — Medium: restore failure semantics differ from the other mutations

**Evidence:** `internal/items/undelete.go:27-37` (untracked feature during review).

After AWS restore succeeds, a `Describe` error is swallowed, returning success
with stale deleted-state UI. A catalog write error instead returns before the
restore-success audit is attempted. Thus a cache problem can conceal a completed
restore from the audit flow. This is the same boundary problem as R14, but in a
separate implementation with different behavior.

**Recommendation:** Record the AWS outcome before reconciliation and communicate
restore success independently from refresh failure. Follow the existing database
clock convention instead of introducing `time.Now()` for catalog freshness.

### R16 — Medium: JSON field serialization silently discards valid data

**Evidence:** `internal/web/static/app.js:125-131`.

Fields are collected into `{}` with `object[key] = value`. A string field named
`__proto__` disappears because assignment invokes the inherited setter; duplicate
names silently replace previous fields. Empty names are silently skipped even
though an empty string is a valid JSON object key. A local JavaScript language
check confirmed the prototype/duplicate behavior; no browser integration was run.

**Recommendation:** Use a null-prototype object or Map, preserve supported keys,
and reject duplicates with a clear field-level error before saving.

### R17 — Medium: deleting every JSON field means “keep the old value”

**Evidence:** `internal/web/static/app.js:131`,
`internal/web/handlers_items.go` function `changeFromForm`.

The field serializer writes an empty string when no keys remain. On edit, an
empty value means unchanged. Removing every field from an existing object
therefore preserves the previous secret instead of storing `{}` or reporting a
validation error. The same empty string carries two incompatible intentions.

**Recommendation:** Represent replacement intent explicitly and serialize an
intentionally empty JSON object as `{}`.

## UX, accessibility, and browser lifecycle

### R18 — Medium: a secret cannot be revealed again after hiding

**Evidence:** `internal/web/templates/item.html:143-149`,
`internal/item/item.go:20`, `internal/web/routes.go` item route registration.

The restored control posts to `/{{.Kind}}/reveal`, producing `/secret/reveal`.
The registered route is `/secrets/reveal`. First reveal works; both automatic
and manual hiding restore a broken control. Existing browser coverage exercises
the repeated-reveal cycle for SSM only.

**Recommendation:** Use `kindPath` consistently and cover both kinds through
multiple reveal/hide cycles.

### R19 — Medium: preview validation opens an error-only modal with no close button

**Evidence:** `internal/web/templates/item_form.html:11`,
`internal/web/templates/partials.html` `problem` fragment,
`internal/web/static/app.js:20-23`, `internal/web/templates/layout.html:10`.

The preview target is dialog content. The htmx configuration deliberately swaps
error responses, and the swap handler opens any nonempty dialog content. Invalid
input therefore opens a plain error fragment with neither a visible dismissal
control nor the normal dialog heading. The source form is inaccessible behind
the modal until the user discovers Escape.

**Recommendation:** Put preview validation beside the editable fields or return
a complete, labelled error dialog with an obvious close control.

### R20 — Low: timezone formatting is lost after htmx swaps

**Evidence:** `internal/web/static/app.js` `localizeTimes`,
`DOMContentLoaded`, and `htmx:afterSwap` handlers.

Local time formatting runs only on the initial document. Searching/filtering
replaces those elements with server-rendered UTC times. The function comment
promises initialization of swapped fragments, but no corresponding call exists.

**Recommendation:** Run fragment initialization, including time formatting,
through one shared lifecycle function after page load and relevant swaps.

### R21 — Low, in-progress work: saving a profile resets local-time preference

**Evidence:** `internal/web/templates/profile.html:5-12`,
`internal/web/handlers_me.go` `updateProfile`,
`internal/access/users.go:165-169`.

The observed form has no timezone field, while the handler reads one and the
service normalizes an omitted value to UTC. Saving name/department therefore
resets a stored local-time preference. Timezone work was changing concurrently;
recheck this finding before scheduling a fix.

**Recommendation:** Add the intended preference control or preserve the existing
preference when omitted.

### R22 — Low: removing a policy rule leaves the live summary stale

**Evidence:** `internal/web/static/app.js:218-222`,
`internal/web/templates/admin_policy.html` preview trigger.

Adding a rule dispatches change; removing one does not. The preview listens for
input, change, and load, so its summary still describes the removed rule until
another edit. A permissions editor should not show a misleading policy summary.

**Recommendation:** Refresh the preview after every structural rule change.

### R23 — Low: value editor fields lack reliable accessible names

**Evidence:** `internal/web/templates/item_form.html:67-84`,
`internal/web/static/app.js:115-117`.

The Value label is not associated with its textarea. Generated key/value fields
have placeholders but no explicit labels, and repeated Remove buttons do not
identify their field. This makes a sensitive editing task harder for assistive
technology users. No screen-reader test was performed.

**Recommendation:** Associate the textarea label and give each generated field
and removal control a meaningful accessible name.

### R24 — Low: disabled permission controls hide explanations from keyboard users

**Evidence:** `internal/web/templates/partials.html:8` `denied-button` fragment.

The explanation exists only in a disabled button's title. Disabled controls are
not normally keyboard-focusable, and title tooltips are unreliable on touch.
The reason a security action is unavailable should be available directly.

**Recommendation:** Show adjacent explanatory text or provide a focusable,
accessible explanation control.

### R25 — Low: second-factor removal skips the documented confirmation convention

**Evidence:** `internal/web/templates/security.html:15-18,39-44,68-72`,
`docs/ui.md` destructive-action convention.

Removing TOTP/passkeys and replacing recovery codes submit immediately, unlike
the shared confirmation flow used for other destructive actions. Accidental
activation can remove an existing recovery mechanism or invalidate saved codes.

**Recommendation:** Confirm the specific consequence using the shared dialog.

## Runtime and delivery

### R26 — Medium: worker ignores a failed health server until shutdown

**Evidence:** `internal/app/app.go:211-225`.

The health server runs in a goroutine, while the foreground waits indefinitely
in `w.Run(ctx)`. Its result is read only after the worker stops. A bind failure
or later listener failure therefore leaves jobs running without reporting that
fatal server error promptly. In Kubernetes this can produce an unready worker
and repeated restarts instead of clear startup failure.

**Recommendation:** Supervise both tasks under a shared cancellation context:
failure of either should stop the other and return the cause promptly.

### R27 — Low: partial web listener startup leaks the first listener

**Evidence:** `internal/app/app.go:253-265`.

`serve` starts each listener immediately. If the second bind fails, it returns
without closing the first listener/server. The current CLI then exits, limiting
the practical impact, but the function's documented all-server lifecycle contract
is false and future in-process callers/tests inherit a running goroutine.

**Recommendation:** Acquire all listeners before serving, or close already
acquired resources on startup failure.

### R28 — Medium: publishing is not gated on the CI result for that commit

**Evidence:** `.github/workflows/publish.yml:5-9,18-20`,
`.github/workflows/release.yml` tag trigger and jobs; `AGENTS.md` release rule.

Publish runs independently on main pushes and can replace `latest` while CI for
that SHA is still running or has failed. Tag release jobs likewise do not verify
the documented green-main prerequisite. External branch protection may reduce
risk, but it is not visible in this repository and does not gate main-push tests.

**Recommendation:** Publish only after successful checks for the exact source
SHA; enforce the tagged release's validated ancestry and version metadata before
publishing any artifacts.

### R29 — Low: main image receives a literal shell expression as its version

**Evidence:** `.github/workflows/publish.yml:38`.

`build-args: VERSION=dev.${GITHUB_SHA::7}` is an action input, not a shell script.
Shell substring expansion does not occur there, so the binary is stamped with
the literal expression instead of the commit abbreviation. Operators lose the
source identity expected in startup logs.

**Recommendation:** Compute the value in a run step/output or use an evaluated
workflow expression, then pass that result to the action.

### R30 — Medium: release checks chart version but not appVersion

**Evidence:** `.github/workflows/release.yml:115-127`,
`charts/platypus/templates/_helpers.tpl` `platypus.image`.

The workflow tells contributors to bump both fields but validates only chart
`version`. If `appVersion` is stale, a new release can package a chart whose
default image still points at the previous application release. Chart and image
publication are also independent jobs, so late validation can leave partial
publication.

**Recommendation:** Check both fields against the release tag in a prerequisite
validation job before any publishing begins.

### R31 — Medium, environment-specific: local Go has a reachable security advisory

**Evidence:** `make vulncheck` reported GO-2026-6809 for local Go 1.27.2,
with a trace from `internal/mfa/passkeys.go:188` through WebAuthn validation to
`crypto/x509.Certificate.Verify`. `go.mod:3` only sets the minimum Go version;
`Dockerfile:2` uses a floating Go 1.26 image tag.

The official advisory describes distrust of compromised intermediate
certificates and lists fixes in Go 1.26.10 and 1.27.3. This establishes the local
scan result, not the version or exploitability of any deployed image.
[Official Go advisory](https://pkg.go.dev/vuln/GO-2026-6809).

**Recommendation:** Use a patched toolchain locally and in CI/container builds,
then rescan the actual release toolchain/artifact. Record exact toolchain and
base-image identities so a floating tag does not obscure what was tested.

## Additional design observations and coverage gaps

These are lower-confidence policy/design questions or broader maintenance work,
not additional confirmed vulnerabilities.

- **Binary rollback policy needs a decision.** `internal/items/change.go:255-257`
  refuses value updates to binary secrets, while rollback promotes a version
  without checking current/target content (`internal/items/change.go` rollback
  branch; `internal/store/awsstore/secrets.go:168-185`). This can replace a
  binary current version with an earlier text version. Decide whether promotion
  is intentionally allowed and align the “binary secrets can't be overwritten”
  promise, UI, and tests. Promotion need not mean the same thing as writing a
  new binary value, so this needs a product contract before being called a bypass.
- **Block/sync audit ordering repeats the same pattern.**
  `internal/appstate/appstate.go` commits the block switch before a required
  audit write and records sync requests best effort. A failed block response can
  still have changed the switch. Treat this alongside R02/R05/R14 rather than
  patching only one caller. Audit requirements should distinguish fail-closed
  reveal events, transactional DB changes, and nontransactional AWS outcomes.
- **Runtime template contracts are mostly implicit.** Go page `Data any`,
  template dictionaries, kind/path strings, and independent fragments make it
  easy for each component to look valid while the combined UI is wrong (R18 is
  a concrete example). Prefer existing typed domain helpers and representative
  rendering/browser tests over introducing a generic UI framework.
- **Test coverage follows happy paths more closely than boundary failures.**
  Add targeted tests for audit insertion failure after state changes, failures
  after the first AWS write, delayed sync callbacks, mutable tags, stale metadata
  forms, safe no-JS submission, repeated reveal for both kinds, and JSON field
  round trips. Raw test count or aggregate coverage would not prove these contracts.
- **Developer checks need clear confidence levels.** `make test-unit` skips
  integrations only because endpoint variables are normally unset. An inherited
  environment changes its scope. The README should distinguish this partial run
  from `make test-deps && make test`, while CI keeps its explicit fail-if-unset
  guard. Do not treat the local successful run in this report as integration proof.
- **Threat-model maintenance needs to follow product changes.** The current
  model still promises universal email verification and no binary overwrites;
  restoration/timezone changes were being added concurrently. Make these
  contracts part of feature completion so operators do not have to infer the
  real behavior from source. Do not simply weaken documented guarantees to match
  defects without deciding the intended product behavior.

## Recommended order of work

1. Fix R01 and add a no-JavaScript sensitive-form regression scenario. Update
   the vulnerable local/build toolchains and rescan (R31).
2. Write down mutation/audit/failure contracts, then address R02-R05 and
   R14-R15 together. Preserve evidence of partial AWS success and audit pruning.
3. Resolve identity-provider assumptions and example-key safety (R06/R09), then
   catalog freshness, Terraform tags, and metadata concurrency (R10-R13).
4. Repair the value editor and reveal/dialog lifecycle (R08/R16-R19), then the
   smaller accessibility and consistency defects (R20-R25).
5. Gate publishing and validate runtime lifecycle/version identity (R26-R30).
6. Run the full isolated database/AWS suite, browser flows for both item kinds,
   chart validation, and artifact-level vulnerability checks on a stable snapshot.

For human maintainability, prioritize explicit operation contracts and a small
set of shared lifecycle helpers. Preserve the readable package structure and
resist replacing concrete service code with broad abstractions. The aim is that
the next human can tell what committed, what was audited, what the user sees,
and what to retry by reading one operation's contract and implementation.
