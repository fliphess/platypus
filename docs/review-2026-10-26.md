## Assessment and highest priorities

The codebase has a usable human-scale structure: small Go packages, explicit
constructors, pure authorization logic, sqlc boundaries, secret-redacting types,
escaped templates, and clear runtime assets. Keep those strengths. The central
problem is that individual pieces are readable but their combined contracts are
inconsistent: what committed, what was audited, what the user sees, and whether
retrying is safe vary by path. UI fixes also tend to add another special case
without validating the whole lifecycle, leaving stale tests/comments and new
regressions.

Prioritize these groups before cosmetic cleanup:

1. **Independent audit integrity:** S01 silently samples audit events and the
   supported log level can suppress every external audit copy. A local proof
   retained only 109 of 1,000 same-second audit messages. S04/S05/Q05 compound
   that weakness with unrecorded pruning and ambiguous committed mutations.
2. **Authorization and factor concurrency:** Q07 can turn two exact-set grants
   into their union; Q08 commits partial group changes; Q13 can remove the last
   active admin despite its lock. S06-S08 cover challenge/factor replacement
   races. Their concurrency scenarios are source/SQL reasoning, not executed
   database exploits.
3. **Broken daily admin/value flows:** U06 targets a nonexistent ancestor, U07
   adds only the first selected team member, U08 traps recovery-only admins,
   and U03-U05 can submit a value different from the visible JSON editor.
   U01 repeatedly rewrites timestamps and schedules itself while idle.
4. **Remote-state consistency:** Q01-Q05 cover stale protection tags, metadata
   conflict detection, cache ordering, false description clearing, and partial
   AWS success. These need an operation contract, not an abstraction rewrite.
5. **Verification and developer safety:** P01 can erase the dev database, P11
   can discard unrelated concurrent source changes, P02 reports success after
   a failed forgery probe, and P03/P08 allow publication/checks to diverge.

The snapshot contains **1 High, 42 Medium, and 30 Low** findings. Those counts
include correctness, UX, operational, and maintainability observations; they
are not 73 exploitable security vulnerabilities. Conditional findings and
design choices are labelled. Severity is qualitative, without fabricated CVSS
precision. Revalidation rows and unnumbered observations are not extra counts.

### S01 — High / security, audit reliability / high confidence — Independent audit logging silently drops events

Evidence: `internal/logging/logging.go:17-24` builds an unchanged `zap.NewProductionConfig()` sampling configuration and applies the configurable log level. `internal/audit/audit.go:111-124` writes every audit event with the identical Info-level message `audit event`. Local pinned dependency source `go.uber.org/zap@v1.28.0/config.go:141-168` documents/sets 100:100 sampling and stderr output.

Scenario: once a process emits more than 100 audit events in the same second, most independent copies are sampled out regardless of their actor, action, or resource fields. Setting the supported log level to warn or error suppresses all audit copies. This defeats threat-model defense 8, particularly when the database audit write fails or a privileged database user tampers with records. The logger also writes stderr despite code/docs explicitly promising stdout; many collectors ingest both, but a stdout-only pipeline loses every copy.

Reproduced with a Go overlay test against the actual `logging.New`: only **109 of 1000** same-second audit entries passed `Core.Check`; a warn logger disabled Info. No snapshot files changed.

Remediation: give audit events an unsampled, independently enabled sink; do not subject mandatory records to application verbosity. Explicitly select the documented stream. Verify bursts and log-level changes retain every audit event.

<a id="s02"></a>

### S02 — Medium / security, authorization identity / high confidence — Lossy group normalization merges distinct identities

Evidence: `internal/auth/groups.go:55-67` applies `textclean.Clean` to provider group names. `internal/textclean/textclean.go:42-62` strips tags/entities/controls and trims. The matching team-link input also uses it (`internal/access/teams.go:36`, supporting inspection).

Scenario: a team linked to `payments` also matches a distinct provider group named `payments<b></b>`. Anyone allowed to manage or join the latter group gains the former team's policies, provided the provider permits those names. Without such provider behavior this remains a collision/correctness defect rather than a demonstrated privilege escalation. A signed token does not prevent the local aliasing.

Reproduced: both identifiers clean to `payments`.

Remediation: use stable opaque provider group IDs and exact equality. If a deployment restricts group names, reject invalid identifiers rather than changing their meaning. Keep human-readable labels separate from authorization keys.

<a id="s03"></a>

### S03 — Medium / security, authentication contract / high confidence; exploitation deployment dependent — Missing email verification is accepted

Evidence: `internal/auth/signed.go:73-79` checks `email_verified` only when present; both signed-header and OIDC use this parser (`signed.go:63`, `oidc.go:157`). `docs/threat-model.md` promises unverified addresses are refused. Tests reject explicit false but do not cover absent verification.

Scenario: a provider that emits a mutable/unverified email without the verification claim can select an existing email-keyed account. The finding is conditional on that provider contract; it does not assert a correctly configured provider allows impersonation. Some trusted signing proxies legitimately omit the claim, so indiscriminately enforcing it would break existing deployments.

Remediation: make the trust contract explicit per mode/provider. OIDC email identity should require affirmative verification; trusted proxy claims that independently establish the address need deliberate configuration/documentation and tests for absence, false, wrong type, and the approved exception.

<a id="s04"></a>

### S04 — Medium / security, audit deletion / high confidence — Pruning can delete records without ever recording the action

Evidence: `internal/audit/trail.go:184-199` deletes in autocommit batches and records the pruning event only after the loop. Errors at line 189 return before recording anything.

Scenario: the first batch succeeds and a later batch fails or the request is cancelled. Some audit history is permanently removed, but there is no pruning event in the table or application audit log because the recorder was never called. This is more serious than a final insert failure, which at least attempts the independent log.

Remediation: durably record the attempt before deleting and record partial completion/failure. Use a bounded background job with its own context and identifiable operation ID; preserve batching without depending on the browser connection for the accountability record.

<a id="s05"></a>

### S05 — Medium / correctness and security accounting / high confidence — Required audit failures report failure after security state already changed

Evidence: `internal/appstate/appstate.go:52-65` changes the block switch before `Audit.Record`; `internal/bootstrap/bootstrap.go:89-105` commits reset before its record, and `bootstrap.go:182-205` commits token consumption/admin grant before completion recording. Supporting revalidation: `internal/web/handlers_adminmode.go:66-72` similarly persists admin mode before recording it.

Scenario: an audit INSERT fails after the preceding state write. The response says the action failed, while access has been unblocked, reset has begun, bootstrap has completed, or admin mode remains active. A retry may then meet a consumed token or changed application state. Logs are attempted, so do not describe this as necessarily leaving no trace; S01 weakens that fallback.

Remediation: provide an audit recorder that participates in the same transaction as database state changes. Emit a carefully defined committed/outcome log outside the transaction. Test audit-insert failure and response/state agreement.

### S06 — Medium / security, replay resistance / high confidence — Passkey ceremony clearing does not atomically consume the challenge

Evidence: `internal/session/session.go:45-50` exposes ceremony state from the request's loaded snapshot; `session.go:193-195` clears it separately and cannot indicate whether another request consumed it. Supporting web code reads the saved state before unconditional clear (`internal/web/handlers_adminmode.go:107-111`, `internal/web/handlers_security.go:212-216`); SQL clear has no condition or `RETURNING` (`database/queries/sessions.sql:22-23`).

Scenario: two requests load the same session before either clears it. Both retain the ceremony and may validate the same assertion. Counterless/synced authenticators cannot be assumed to reject that duplicate, and concurrent loads can race even for a counted credential. This violates single-use semantics; it does not demonstrate authentication without an original valid assertion.

Remediation: atomically take-and-clear the ceremony with `UPDATE ... RETURNING`, including expiry and expected purpose/challenge checks. Only the request receiving a row may finish verification. Exercise concurrent finishes.

### S07 — Medium / security, recovery-code lifecycle / high confidence in race; not database-reproduced — Concurrent regeneration can retain both code batches

Evidence: `internal/mfa/recovery.go:38-47` replaces codes using `DELETE` then inserts in a transaction, without a user-row/advisory lock. `database/queries/mfa.sql` provides ordinary delete/insert statements; there is no per-user generation key/uniqueness boundary.

Scenario: two initial issuances for one user both delete the empty set, each inserts ten rows, then both commit. Twenty codes remain valid even though issuance promises to replace all earlier codes. Two tabs, a double submit, or multiple replicas can trigger it; requests still require factor-management authority.

Remediation: serialize replacement by locking the user row inside the transaction, or model an active recovery generation and atomically replace its ID. Add a concurrent issuance test verifying exactly the final ten codes remain valid.

### S08 — Low / correctness and UX, MFA race / high confidence — A code can confirm a different TOTP secret than the one checked

### Q01 — SSM management tags never expire, and unreadable tags permit mutations

**Severity:** Medium. **Category:** correctness / protection consistency. **Confidence:** high; code paths directly establish the behavior.

### Q02 — Secret metadata edits can silently overwrite stale forms

**Severity:** Medium. **Category:** correctness / concurrency. **Confidence:** high.

**Locations:** `internal/catalog/catalog.go:129-135`; `internal/store/awsstore/secrets.go:152-165`; `internal/store/storetest/storetest.go:258-270`.

The form token and `UpdateDescription` compare only the current secret value version. Description changes do not create a value version; the contract test explicitly checks that they do not. **Severity:** Medium. **Category:** correctness / cache concurrency. **Confidence:** high.

### Q05 — Successful AWS mutations can be reported and audited as entirely failed operations

**Severity:** Medium. **Category:** correctness / audit integrity / UX. **Confidence:** high.

**Locations:** `internal/items/change.go:91-112,193-228,252-267`; `internal/store/awsstore/parameters.go:138-141,176-179`; `internal/store/awsstore/secrets.go:126-129,142-149`.

The tests only cover single-line items with prose before them. This is a limitation rather than a demonstrated defect in the current page contents; the heuristic heading/term grammar makes otherwise ordinary text edits depend on undocumented formatting details.

**Remediation:** Preserve ordered paragraph/list nodes, or specify and validate a narrower source grammar with an actionable loader error. Add wrapped-list and prose-after-list cases. Keep HTML escaping in HTMLText: its escape-before-code-wrapping approach is sound.

### U01 — Medium / high confidence: local-time formatting schedules itself forever

**Evidence:** `internal/web/static/app.js:38-42`, `:437-443`.

The body-wide MutationObserver schedules `localizeTimes()` after every child mutation. That function sets every time element's `textContent` unconditionally, which replaces child text nodes and triggers the same observer again. A user selecting local time on a page with timestamps gets a permanent cycle of whole-document queries and DOM writes at roughly 40 ms intervals, even while idle. Large audit pages amplify the cost and repeated replacements can disrupt selection/assistive announcements. An isolated run of the actual code produced 11 rewrites after initialization plus 10 timer turns, with another timer still pending and no external changes.

**Remedy:** Make rendering idempotent (`textContent !== desired` before writing), observe only relevant additions, or remove the observer now that timestamps render server-side. Use one explicit fragment initializer rather than server formatting plus afterSwap plus afterSettle plus pageshow plus an unconditional observer.

<a id="u02"></a>

### U02 — Medium / high confidence: removing policy rules never marks the change or refreshes the summary

**Evidence:** `internal/web/static/app.js:302-308`, `:495-506`; `internal/web/templates/admin_policy.html:24`, `:39-42`.

The removal handler first detaches the rule, then asks the detached button for its closest form. The form is now null, so the intended change event never fires. On a freshly loaded existing policy, deleting a rule leaves Save disabled, the summary still describes the deleted rule, and the unsaved-change warning is not armed. If another field had already enabled Save, the rule can disappear while the summary remains stale. This is the attempted fix for prior R22, but the ordering makes it ineffective.

**Remedy:** Capture the form/list before removal (or use the `editor` closure) and dispatch one structural-change event after adding/removing a row. Have that event update summary and dirty state together. Test removal as the only edit on a freshly opened policy.

<a id="u03"></a>

### U03 — Medium / high confidence: duplicate JSON fields warn but submit an older, different value

**Evidence:** `internal/web/static/app.js:170-188`, `:223-234`; `internal/web/templates/item_form.html:11`, `:89`.

Duplicate detection returns before updating the hidden textarea. It neither prevents form submission nor sets custom validity. The form submits that textarea, not the visible row inputs. A user who introduces a duplicate sees a warning but can Save and confirm a stale previously valid object that differs from the visible editor. Switching modes also continues after the failed synchronization and can discard the visible edits. The isolated actual-code check showed two visible `a` keys, a duplicate warning, and the submitted textarea still containing the old `{a,b}` object.

**Remedy:** Model the serializer as a success/failure result, block preview/save and mode switching while invalid, and associate the duplicate error with its input. Test the submitted value after invalid edits, not just whether a warning appears.

<a id="u04"></a>

### U04 — Medium / high confidence: deleting the last JSON field still means “keep the old secret”

**Evidence:** `internal/web/static/app.js:181-187`; `internal/web/handlers_items.go:405-407`.

The new `{}` branch requires that at least one row still exists. Clicking Remove on the final row leaves zero rows, bypasses that branch, and serializes `""`. The handler interprets this as no replacement. Removing all fields therefore preserves the existing secret. The actual-code isolated check produced `rows: 0, submitted: ""`. The comment saying “Every field removed” describes the opposite condition.

**Remedy:** Serialize an intentional empty field object as `{}` regardless of remaining row count, and distinguish replacement intent from an untouched empty editor. Add a browser regression that removes the final row and verifies the stored value.

### U05 — Medium / high confidence: valid empty-string JSON keys still disappear

**Evidence:** `internal/web/static/app.js:174`, `:219-220`.

Loading `{"":"keep","a":"old"}` into fields creates a row for the empty key. Editing the other row skips the empty-name row during synchronization and saves only `a`; the previously valid key is silently lost. The `Map` fix handles `__proto__`, but does not resolve this part of prior R16. Confirmed using the actual editor function with a minimal DOM stub.

**Remedy:** Preserve empty-string keys, or refuse field mode for objects containing them with an explicit explanation. Distinguish an intentionally blank new row from an existing JSON key rather than silently dropping it.

### U06 — Medium / high confidence: user-detail admin actions have an invalid htmx target

**Evidence:** `internal/web/templates/admin_user.html:24`, `:29`, `:35`; vendored htmx `m`, `g`, and `fe` functions (`internal/web/static/htmx-2.0.11.min.js:1`).

**Remedy:** Give the account-message container an explicit ID, or place the target attribute on the card and use an appropriate descendant selector. Exercise these buttons through a browser, including a refused last-admin operation.

**Recommendation:** Validate exact source SHA, required checks, release ancestry,
and both version fields in a prerequisite job/workflow before any publishing.
Use a deliberate promotion policy for the shared `latest` pointer.

<a id="p04"></a>

### P04 — Medium: startup probes do not allow the OIDC initialization budget

**Category:** availability. **Confidence:** high from source timing; no cluster run.
**Evidence:** `charts/platypus/templates/_helpers.tpl:97-108`;
`internal/app/app.go` `RunWeb` and `discoverOIDC`; `internal/auth/auth.go`
ten-second HTTP client.

Web health listeners start only after docs loading and authentication discovery.
OIDC discovery can retry ten times with network timeouts and three-second waits,
but the chart has immediate liveness checks and no startup probe or startup
allowance. During slow identity-provider recovery, Kubernetes can restart the
container after the default three liveness failures, before its intended startup
retry budget has elapsed. Exact timing depends on kubelet scheduling.

**Recommendation:** Define a startup probe budget matching bounded initialization,
or bring up separate startup-aware health handling earlier. Keep readiness and
liveness meanings separate. Kubernetes documents that a startup probe suppresses
liveness/readiness until startup succeeds:
[probe documentation](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-probes/).

<a id="p05"></a>

### P05 — Medium, CNI dependent: the network policy has no Pod Identity credential path

**Category:** deployment compatibility. **Confidence:** high for missing rule;
runtime impact depends on enforcement of node/link-local traffic.
**Evidence:** `charts/platypus/templates/networkpolicy.yaml:48-71`;
README and deployment checklist advertise EKS Pod Identity.

The policy permits only DNS, the Postgres port, and TCP 443. EKS Pod Identity
credentials are retrieved over HTTP at `169.254.170.23`, a path absent from those
rules. A CNI enforcing egress to that endpoint can block credential acquisition
even though HTTPS AWS calls are allowed. Some CNIs exempt or specially handle
host-network/link-local destinations; this is not a universal EKS failure claim.
AWS documents the HTTP URI and injected environment variable:
[Pod Identity operation](https://docs.aws.amazon.com/eks/latest/userguide/pod-id-how-it-works.html).

**Recommendation:** Add an explicit, narrowly scoped Pod Identity option/rule,
document CNI requirements, and exercise that credential path in deployment tests.
Avoid solving it by permitting unrestricted HTTP egress.

<a id="p06"></a>

### P06 — Medium: advertised listener configuration can disconnect chart routing and probes

**Category:** configuration consistency. **Confidence:** high, source-confirmed.
**Evidence:** `charts/platypus/templates/_helpers.tpl:78-108`,
`charts/platypus/templates/service.yaml`; `internal/config/vars.go` HTTP/health
address declarations; `charts/platypus/values.yaml` free environment configuration.

Users can set `PLATYPUS_HTTP_ADDR` and `PLATYPUS_HEALTH_ADDR` through chart config,
but container named ports and probes stay at 8080/8081. Setting a different valid
port starts the app where the Service/probes do not reach it. These settings are
documented without a chart restriction or matching chart fields.

**Recommendation:** Derive listener env and target/probe ports from shared chart
values, or reject/document unsupported listener overrides in chart deployments.
Validate port consistency in rendered-manifest tests.

<a id="p07"></a>

### P07 — Medium: the “least you need” example passes Helm checks but cannot start

**Category:** installation UX / example accuracy. **Confidence:** high.
**Evidence:** `charts/platypus/ci/minimal-values.yaml:1,7-12`, chart production
environment default, `internal/config/config.go` known-key rejection.

The earlier unsafe public-key acceptance has been fixed for the exact example
key. The example still supplies that key and inherits production mode. Therefore
copying the advertised minimal values and supplying a real DB password still
fails configuration validation. Helm lint/template pass because they do not
run configuration loading. Do not remove the key guard to repair the example.

**Recommendation:** Separate nondeployable rendering fixtures from installation
examples. Show an existing Secret or explicit generated-key step and validate
the deployment example's configuration contract. S09 covers a remaining alternate
encoding weakness in the guard itself.

<a id="p08"></a>

### P08 — Medium: the documented verification gate and CI enforce different checks

**Category:** process consistency / regression prevention. **Confidence:** high.
**Evidence:** `AGENTS.md` gate/style rules; `Makefile:108-110`;
`.github/workflows/ci.yml:48-93`.

`make verify` claims to be “Everything CI must pass” but omits vulncheck, chart
checks, and smoke. CI does not invoke it and omits `css-check`, so it can accept
a stale generated stylesheet despite the explicit repository invariant. The
snapshot actually fails `make css-check` (U11), demonstrating that this gap is
material. The verify prerequisites also assume test dependencies are already up.

**Recommendation:** Define one check matrix with clear dependency setup and make
CI/local targets implement that matrix. Keep read-only verification separate
from regeneration, which modifies files. Include the CSS equality check in CI.

<a id="p09"></a>

### P09 — Low: dev-reload treats a failed connection as readiness

**Category:** developer feedback. **Confidence:** high.
**Evidence:** `Makefile:75-80`.

Curl transport failure emits `000`, and `|| true` masks its failure. The readiness
predicate accepts any nonempty status other than 502, so it reports “dev stack
ready (000)” when nothing is listening. It also accepts 503/504/500. This hides
the exact startup/reload problems the target is intended to diagnose.

**Recommendation:** Check curl success and a small set of expected successful or
authentication statuses. Report the last failure on timeout.

<a id="p10"></a>

### P10 — Medium: the large-data seeder fails SQL while appearing successful

**Category:** development correctness / misleading fixtures. **Confidence:** high
from schema and psql invocation; database execution not performed.
**Evidence:** `scripts/dev-seed-large.sh:10,26-37`;
`database/migrations/updates/V20261025.0100__initial_schema.sql:250-263`.

The insert refers to `audit_events.resource_type`, but the table column is
`resource_kind`. It also inserts NULL for non-null `reason`. These errors occur
inside the same transaction as user insertion, so the intended seed is rolled
back. Psql is not given `ON_ERROR_STOP`, so ordinary SQL errors need not make
the shell fail, and the script can print the reassuring page links anyway.
Its event kinds/actions also use obsolete spellings rather than application
constants. The user-count argument is interpolated directly into SQL without
even numeric validation; this is a local trusted utility, not a remote injection
endpoint, but input mistakes are needlessly dangerous under a superuser.

**Recommendation:** Repair the schema/action vocabulary, fail on the first SQL
error, validate a bounded integer count, and verify inserted counts in a disposable
database. Keep fixture vocabulary aligned with application domain constants.

<a id="p11"></a>

### P11 — Medium: mutation-test cleanup can discard unrelated agent work

**Category:** shared-workspace data safety. **Confidence:** high.
**Evidence:** `scripts/guards-prove.sh:10-16,42-55`.

The script checks the tree once, then installs an EXIT trap that checks out all
of `internal`, `cmd`, and `database`. Any human/agent edits arriving after the
initial check can be discarded, including files the script never mutated. It
also shares `/tmp/guards-prove.log` between runs and edits generated CSS directly.
The initial clean check is insufficient isolation for a multi-agent workspace.

**Recommendation:** Run mutation experiments in a disposable worktree/copy,
restore only owned files, and use unique logs. Do not execute this script in the
shared working directory; this review did not run it.

### P12 — Low: shipped docs and UI conventions contradict current product flows

**Category:** human maintainability / product consistency. **Confidence:** high.
**Evidence:** `internal/docs/pages/40-admin-guide.txt` Users/Teams sections;
`docs/ui.md` principles 4/8 and picker/dialog components;
`internal/web/templates/admin_user_new.html`, `admin_confirm.html`;
`internal/web/handlers_admin_access.go` account creation and candidate handling.

The guide says users can be added by email on a team's page, then says people
who have not logged in cannot be picked and addresses are never typed. The app
has typed-email account creation and a current multi-select member editor.
The UI spec requires destructive confirmation in a dialog, while new assignment
confirmation uses a full page. It also defines both “nothing is ever clipped”
dropout rows and generic truncation rules without clearly assigning ownership.
These are design decisions to reconcile, not proof one particular UI is wrong.

**Recommendation:** Decide the supported invitation/selection/confirmation flows,
then update code comments, in-app guidance, UI conventions, and tests together.
Keep standards descriptive and enforceable; avoid absolute claims already
contradicted by normal product behavior. Q15/U12 describe related code/test drift.

<a id="p13"></a>

### P13 — Low: recovery guidance backs up the database without explaining key recovery

**Category:** operational documentation gap. **Confidence:** high for missing
guidance; no claim that a deployment lacks its own backups.
**Evidence:** `docs/deployment-checklist.md` Database and Secrets sections;
`internal/seal/seal.go`; configuration's encryption-key contract.

The checklist explicitly calls for DB backups containing second factors, but
does not explain retaining the matching encryption key, restoring the pair,
or what rotation means for existing ciphertext. Restoring the DB with a new key
cannot decrypt stored factors. External secret-store retention may already solve
this in a deployment; the application recovery contract leaves it implicit.

**Recommendation:** Document coordinated key/DB recovery, key identification and
retention, and the supported rotation/reset procedure without exposing key values.

<a id="p14"></a>

### P14 — Low: production image identity remains mutable and the chart cannot pin a digest

**Category:** reproducibility / supply-chain hardening. **Confidence:** high.
**Evidence:** `Dockerfile:2`, `charts/platypus/templates/_helpers.tpl:44`,
`charts/platypus/values.yaml` image settings; publish/release moving tags.

The builder now pins a patched Go version, an improvement, but still references
a mutable tag. The chart always constructs `repository:tag` and exposes no digest
option. Reusing a chart version or mutable `latest` with IfNotPresent can produce
different image bytes across nodes/restarts. Signed/provenance-enabled build
metadata does not make tags immutable. This is a hardening gap, not evidence of
a compromised artifact. Memory-only limits are deliberate project defaults and
are not called a security vulnerability here simply for lacking CPU limits.

**Recommendation:** Support image digest selection and record/pin the tested
base-image digest in releases; reserve moving tags for intentional development
use. Retain the existing non-root/read-only/drop-capabilities defaults.

<a id="p15"></a>

### P15 — Low: browser verification resolves dependencies with npm install in a writable tree

**Category:** repeatability / developer ergonomics. **Confidence:** high.
**Evidence:** `e2e/run.sh:42-44`, `e2e/package-lock.json`.

The test runner mounts the repository's e2e directory writable and runs
`npm install` rather than a lock-enforcing clean install. Manifest/lock drift can
be repaired during verification, leaving test results tied to newly resolved
dependencies and modifying developer files. The top-level Playwright pin helps,
but does not establish immutable lockfile use.

**Recommendation:** Use `npm ci` and isolate install/cache/output directories;
mount only intended output locations writable. Keep browser image and package
versions coordinated and report dependency-install failure distinctly.

<a id="p16"></a>

### P16 — Low: shell conventions and tool prerequisites are inconsistent

**Category:** maintainability / documented standards. **Confidence:** high.
**Evidence:** `e2e/run.sh:12-24`; `deploy/dev/seed.sh:1-12`;
`scripts/sqlfluff.sh:18`; `.pre-commit-config.yaml`; `scripts/*.sh`.

The browser runner stores a multiword command in a scalar and executes it by
word splitting, rather than a Bash array. Most scripts use strict Bash, while
the dev seeder uses POSIX sh and masks every AWS error as “already seeded.” The
container may require POSIX sh, but that exception and error policy are not
documented. SQL linting shells out to Python although developer prerequisites
focus on Docker/Go. Shell formatting differs across scripts; shfmt reported
differences, while `shellcheck --norc --severity=warning` passed. A separate
unqualified ShellCheck run inherited machine-wide style rules, which are not
mistaken for repository requirements here.

**Recommendation:** Use arrays for command lists, document required interpreters
and intentional POSIX exceptions, distinguish known AlreadyExists errors from
connectivity/permission failures, and enforce a single agreed formatter/linter
configuration in the project. Do not turn each formatting difference into its
own finding.

<a id="p17"></a>

### P17 — Medium: a late CSV failure can append HTML to an already-started export

**Category:** export correctness / failure handling. **Confidence:** high from
streaming/error control flow; no induced database failure executed.
**Evidence:** `internal/web/handlers_admin.go:193-198`;
`internal/audit/trail.go:128-166`; `internal/web/render.go` generic `handle/fail`.

CSV export writes batches directly to the response, then returns any later
query/write error to the ordinary HTML error handler. Once enough records have
flushed the CSV buffer, response status/headers are committed. A later error
cannot replace them; the handler instead attempts to append an HTML error page
to a partial CSV with the original success status and attachment filename.
An administrator can receive a corrupt or incomplete audit export presented as
a successful download. This is separate from U10's stale filter link.

**Recommendation:** Define an export-specific error contract. Generate into a
bounded spool before committing the response, or deliberately terminate a failed
stream and log/report its failure without adding HTML. Test failure after at
least one buffer/batch has been written.

<a id="p18"></a>

### P18 — Low: partial listener startup leaves an earlier server running

**Category:** lifecycle correctness. **Confidence:** high, source-confirmed.
**Evidence:** `internal/app/app.go:253-265` (`serve` listener loop).

The first listener starts serving before the next is acquired. If the second
bind fails, the function returns without shutting down the first listener or
goroutine. The current CLI exits immediately afterward, limiting practical
impact, but the documented all-server shutdown contract is false and in-process
callers or future retries can inherit a leaked listener. This is prior R27,
still present, distinct from the worker not observing its health-server error.

**Recommendation:** Acquire all listeners before serving, or close every acquired
resource on startup failure. Verify an occupied second address leaves no first
listener behind.

### Additional observations, not extra defect counts

- `docs/security.md` deliberately chooses public disclosure and no embargo. This
  is an explicit maintenance policy, not a covert security vulnerability. It
  should be an informed product decision for a secrets-management application.
- `docs/assets.md` still tells source contributors to edit generated style.css
  for branding, whereas AGENTS.md says edit CSS fragments. A deployed override
  can legitimately edit the bundle; the docs should distinguish those workflows.
- The default NetworkPolicy intentionally permits broad HTTPS/Postgres egress
  when destination peers are empty, and ingress from the entire gateway
  namespace. The values document narrowing them. These accepted operator choices
  are not silently reclassified as remotely exploitable defects.
- Helm lint/template passed for all three examples. This proves rendering, not
  installed CRD compatibility or cross-resource runtime behavior. `helm-lint`
  uses `-ignore-missing-schemas`, so custom TrafficPolicy/ExternalSecret/HTTPRoute
  correctness may receive little validation without installed/pinned schemas.
- License, ignore files, checksum lists, dependency locks, and generated files
  were reviewed for their appropriate role. Vendored htmx received checksum and
  call-site checks, not a claim of a full independent library security audit.

## Suggested implementation sequence

Keep remediation separate from this review. Start with the audit sink and the
transaction/concurrency contracts; fix the broken admin/recovery/value-editor
flows with targeted regressions; then repair cache/version semantics and safe
verification/publishing. Handle low-priority comment/CSS/API cleanup as a
coherence pass after agreeing the final product behavior.

For database changes, keep migrations compatible with the previous release and
regenerate sqlc normally. For external writes, a database transaction cannot
make AWS atomic: expose completed steps and reconciliation status explicitly.
For UI changes, use one shared fragment initializer and test submitted values
and final stored state, rather than only labels, warning presence, or pixels.

Re-run the complete isolated Postgres/AWS suite, actual browser flows for both
item kinds, rendered/installed chart validation, and artifact vulnerability
checks after fixes on a stable source version. The passing partial checks here
are evidence of the checks listed, not proof the product is ready to release.
